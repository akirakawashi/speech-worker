# Разработка и проверки

Работаем в собственном окружении speech-worker. Python 3.12; ffmpeg и ffprobe
нужны для настоящей подготовки аудио. Команды создания окружения находятся
в [README](../README.md#локальное-окружение).

## Зависимости и установка

Используем UV 0.11.18+ и сборщик `uv_build`. Настройки проекта пересозданы
через `uv init --bare --package --build-backend uv`. `pyproject.toml` описывает
зависимости исполнения, группу `dev`, команды и проверки; `uv.lock` фиксирует
версии и хеши пакетов. Python 3.12 выбран в `.python-version`. Отдельных
requirements-файлов нет.

```bash
uv sync --locked
uv run --locked speech-worker --help
uv lock --check
uv build
```

UV сам создаёт `.venv` и устанавливает проект. При пересоздании сохранены
проверенные версии библиотек. `uv add`, `uv remove` и `uv lock` меняют зависимости;
`uv sync --locked` проверяет актуальность lock-файла перед установкой.
После обновления проверяем тесты и сборку образа.

Docker использует тот же `uv.lock`: сначала устанавливает зависимости через
`uv sync --locked --no-dev --no-install-project`, затем устанавливает
сам проект через `uv sync --locked --no-dev --no-editable`. Команды, Python-модули
и JSON-справочники входят в устанавливаемый пакет. Папки `*.egg-info` в исходниках
не создаются. Генерируемые `.venv`, `dist` и кэши в Git не входят.
Исходники и тесты при смене инструментов не переписывались.

Список зависимостей не включает веб-сервер, авторизацию API, PyTorch, CUDA
или GigaAM.

## Статические проверки

Запускаем Ruff, ruff format --check и строгий mypy src в окружении проекта.
Тест архитектуры запрещает обход границ слоёв и импорты старого app.
Docstring новой функции объясняет действие, вход, выход, значимые ошибки
и побочные эффекты. Не подавляем ошибки ради успешного прогона.

## PostgreSQL под тестами

SPEECH_POSTGRES_TEST_URL направляем только в отдельную пустую тестовую базу.
Тесты очищают таблицы речи; speech, speech_test и рабочие базы не используем.
Имя должно содержать test, tests или ci как отдельную часть. Существующая
выделенная база — speech_whisper_test; для отдельного временного контейнера
можно создать speech_worker_test.

Перед прогоном применяем существующие миграции speech-backend к этой тестовой
базе до sp_0016_evaluation_jobs. В самом воркере миграций нет.
SPEECH_REQUIRE_LIVE_PROOFS=1 делает пропуск проверок PostgreSQL неуспехом прогона.
SQL очереди, lease и блокировки проверяются на PostgreSQL, SQLite их не заменяет.

## Что проверяется

- Реальная PostgreSQL: claim, nonce, heartbeat, потеря lease, приоритеты,
  буфер доставки, восстановление после аварии и защита нового захвата.
- Получение и ASR, источники NCC/Телфина, метаданные классификации,
  MinIO и HTTP-транспорт доставки; анализ/оценка проверяются в бэкенде.
- Запуск выбранных этапов, неверные аргументы и закрытие пула при остановке.
- Очистка после успеха, ошибки, отмены и завершения процесса без finally;
  сохранение каталогов другого активного обработчика.
- Квитанция бэкенда, неизменный повтор после потери ответа, отсрочка при
  сетевом отказе и отсутствие локального store/complete распознавания.

Реестр и runtime принимают только ingest/transcribe. LLM-код и его
дублирующие тесты удалены из воркера. Сборщик возвращает только
этапы своего реестра и выбранных полос. CPU-анализ и оценка реализованы
в бэкенде одним процессом `speech-process`:
[запуск и гарантии](../../speech-backend/docs/evaluation-processing.md).

Проверки HTTP используют синтетические ответы и подставные транспорты;
они не измеряют качество или скорость настоящего Whisper/LLM.
После настройки сервера нужен отдельный прогон на его реальных HTTP-сервисах.

Для изменений только документации проверяем локальные ссылки и согласованность.
