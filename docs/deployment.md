# Запуск на GPU-сервере

Инструкция относится к текущему переходному коду. Цель по решению 13.10.2026 —
воркер получения/распознавания/доставки и отдельный фон бэкенда для LLM и
сохранения итогов. Этот переход ещё не реализован; его выпуск требует
согласованного запуска двух исполнителей.
[Главное правило](../../speech-backend/docs/processing-ownership.md).

Воркеру нужны CPU, ffmpeg и доступ к существующим HTTP-сервисам.
Whisper работает в своём контейнере. MinIO находится на отдельной машине;
GPU и CUDA воркеру не требуются. GigaAM не подключён.

## Настройки и схема

Создать `.env` из [.env.example](../.env.example) и заполнить адрес общей базы,
MinIO, Whisper, API бэкенда, адреса LLM и данные используемых источников.
`SPEECH_WORKER_API_TOKEN` должен совпадать с ключом бэкенда.
Бэкенд выбирает промпты, model ID и ограничения ответа; воркер хранит
адреса, ключи и таймауты HTTP-серверов.

Применить миграции бэкенда до `sp_0016_evaluation_jobs`.
Воркер только проверяет готовность схемы и не запускает миграции.

## Одна команда

Для запуска без контейнера:

```bash
uv sync --locked
uv run --locked speech-worker
```

Или в Docker:

```bash
docker compose up -d --build
docker compose logs -f worker
```

Один процесс обслуживает полосы `daily,backfill` и четыре вида задания:
`ingest`, `transcribe`, `analyze` и `evaluate`. Один обработчик выполняет
одно задание за раз; аудио передаётся в Whisper по одному файлу.

В том же процессе независимо работают лёгкие циклы приёма NCC, Телфина
и постановки оценки. Они получают план от бэкенда, регистрируют метаданные
и не вызывают модели. Долгий запрос источника не задерживает обработку очереди.
Один источник не начинает следующий прогон до завершения предыдущего.

| Действие | Сохранённое расписание |
| --- | --- |
| NCC | Каждые 15 минут; днём сразу половина, остальные с 19:00; ночью всё сразу |
| Телфин | Раз в час, с 19:00 до 07:00 по Москве; приоритет 20 |
| Оценка | Постановка каждые 15 минут, до 100 готовых звонков Телфина |

Оценка выполняется в общей очереди последовательно с другими заданиями.
Отдельные таймеры и контейнеры приёма не нужны; их шаблоны удалены.
Интервалы, ночь и дневная доля задаются в настройках бэкенда.
[Контракт и правила расписания](../../speech-backend/docs/worker-runtime.md).

## Ручные режимы

```bash
uv run --locked speech-worker --sources ncc
uv run --locked speech-worker --queue-only
uv run --locked speech-worker --once
uv run --locked speech-worker --stages ingest,transcribe --sources ncc
uv run --locked speech-evaluate --all --limit 100 --skip-failed --apply
```

`--sources` ограничивает автоматический приём; неиспользуемый Телфин можно
исключить. `--queue-only` отключает автоматический приём и постановку оценки,
сохраняя обработку уже поставленных заданий. `--once` обрабатывает не больше
одного задания и не запускает расписание. `--stages` ограничивает обработчики;
нужно настроить только выбранные этапы.

`speech-evaluate` проверяет охват без `--apply`, с ним ставит задания.
Готовые оценки появятся после их обработки постоянным воркером.
`speech-ingest` и `speech-backfill` остаются ручными инструментами.

## Контейнер, сеть и файлы

Compose использует сеть Linux-хоста: `127.0.0.1` в адресе Whisper указывает
на HTTP-порт GPU-сервера. Для MinIO указать адрес его отдельной машины.
Том `worker-tmp` принадлежит временным копиям воркера; UID/GID процесса — 10001.

Для `local_export` добавить read-only mount каталога записей и указать
`SPEECH_NCC_EXPORT_DIR` внутри контейнера. Для `reporting_view` заполнить
настройки отчётной базы NCC и HTTP-доступа к записям. Аудио в образ не входит.

## Переключение и остановка

Остановить старые воркеры и таймеры, обслуживающие эту базу, применить
миграцию, обновить API и запустить один новый воркер. Остановку действующих
сервисов и переключение сервера эти изменения автоматически не выполняют.
Исходные проекты и рабочие `.env` сохранены.

```bash
docker compose stop worker
```

SIGTERM прекращает приём и новые захваты; текущее задание заканчивается.
Compose даёт на завершение 35 минут, затем принудительно останавливает процесс.
При обычной ошибке временное аудио удаляется контекстом этапа. После аварии
следующий запуск убирает собственные свободные каталоги по файловым блокировкам.

Оригинал в MinIO сохраняется. За временные файлы внутри контейнера Whisper
отвечает сам Whisper; его очистка проверяется на сервере.
