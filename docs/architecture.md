# Архитектура воркера

`speech-worker` — самостоятельный проект со своей сборкой и окружением.
Решение владельца 12.10.2026: разворачиваем на GPU-сервере без Kubernetes.
Текущая реализация использует существующий Whisper по HTTP.
GigaAM отложен: кода адаптера, настроек движка и зависимостей модели в проекте нет.

## Ответственность и ресурсы

Воркер перечисляет звонки NCC и Телфина, получает записи, сохраняет оригиналы
в MinIO, готовит аудио, вызывает Whisper и существующие HTTP-приложения
Dify/LLM, записывает результаты и обслуживает очередь PostgreSQL.

GPU использует контейнер Whisper. Воркеру нужны CPU для ffmpeg, оперативная
память и временный диск. LLM остаётся отдельным HTTP-сервисом.
MinIO находится на другой машине; внутренняя сеть — 10 Гбит/с по словам владельца.
Бэкенд и фронтенд предназначены для CPU в Kubernetes.

## Слои

| Пакет | Ответственность |
|---|---|
| `src/presentation` | CLI, разбор входных параметров, вывод результата |
| `src/application` | Сценарии, Pydantic DTO и порты внешних операций |
| `src/domain` | Правила обработки звонков, очередности и оценки продаж |
| `src/infrastructure` | PostgreSQL, очередь, источники записей, MinIO, ffmpeg, Whisper и Dify/LLM по HTTP |
| `src/setting` | Pydantic Settings только для фоновых процессов |
| `src/di` | Сборка выбранных ресурсов и управление их временем жизни |

Presentation вызывает application; application применяет domain и порты.
Infrastructure реализует порты, DI внедряет реализации. Domain не зависит
от других слоёв; application не импортирует infrastructure.
Точки входа CLI вызывают сборку DI после разбора аргументов.
Границы проверяет [тест архитектуры](../tests/test_architecture.py).

Параметры основного воркера проверяются через [WorkerOptions](../src/application/dto/worker.py).
Распознавание вызывается через порт `RecordingTranscriber` и возвращает
единый DTO текста, сегментов и таймкодов. HTTP-объекты, соединения БД и
файловые блокировки остаются в infrastructure.

## Целевой пайплайн

1. `speech-ingest` или API ставит задания в существующую `speech_jobs`.
   Передаются идентификаторы, этап и ссылки на данные.
2. Один процесс воркера последовательно захватывает задания, удерживает
   lease с heartbeat и возвращает просроченные аренды в обработку.
   Сохраняются приоритеты NCC, Телфина и истории, а также `not_before`.
3. `ingest` скачивает запись во временный каталог, измеряет её через
   ffprobe и сохраняет оригинал в MinIO. Уже сохранённый объект
   повторно не загружается из источника.
4. `transcribe` скачивает оригинал из MinIO, готовит WAV mono 16 кГц и
   отправляет один файл в существующий Whisper по HTTP. Стереооригинал
   используется для ролей участников; сегменты после конца аудио отсекаются.
5. Долгие операции завершаются вне транзакции. Запись результата,
   завершение задания и постановка следующего этапа выполняются вместе.
   При потере lease запись откатывается, чтобы не затереть чужой результат.
6. `analyze` вызывает существующее приложение разбора Dify и сохраняет
   результат. Воркфлоу перенесены без изменений.
7. Бэкенд читает сохранённые данные и выдаёт их фронтенду.
   Оценка продаж выполняется отдельно командой `speech-evaluate`, только
   для Телфина; нового этапа оценки в очередь не добавлено.

При ошибке сохраняется класс отказа, применяется существующая задержка
и ограничение попыток. Повторы не должны удваивать объект, транскрипт
или следующие задания. Обезличивание текста не возвращается.

## Время жизни и очистка

При запуске DI собирает зависимости только выбранных этапов и проверяет
ревизию схемы и необходимые таблицы. Пул PostgreSQL создаётся, используется
и закрывается в одном event loop, включая ошибку запуска и режим `--once`.
Сигнал остановки завершает текущее задание перед выходом.

Корень временного аудио задаёт `SPEECH_WORKER_TEMP_DIR`. Каждый каталог этапа
защищён файловой блокировкой Linux. После успеха, исключения или отмены он
удаляется. При запуске проверяются оставшиеся каталоги: занятые пропускаются,
свободные собственные каталоги удаляются. Создание каталогов и уборка
сериализованы отдельной блокировкой корня, чтобы не удалить создаваемое задание.

Исходная запись в MinIO остаётся до удаления отдельным сценарием хранения.
За файлы, принятые внутри контейнера Whisper, отвечает сам сервис модели;
фактическая очистка в работающем образе ещё не проверена.
Подробнее: [очистка](audio-flow.md#ответственность-за-очистку).

## Сценарии Dify

Решение владельца 12.10.2026: сценарии Dify хранятся только в этом проекте,
в `dify/speech/`. Дубли в `speech-backend` удалены. В составе папки:

| Файл | Назначение |
|---|---|
| [speech-call-analysis.dify.yml](../dify/speech/speech-call-analysis.dify.yml) | Анализ звонка: классификация, тональность, резюме, роли и причина обращения |
| [speech-call-reason.dify.yml](../dify/speech/speech-call-reason.dify.yml) | Определение причины обращения по расшифровке |
| [speech-free-classification.dify.yml](../dify/speech/speech-free-classification.dify.yml) | Свободная классификация обращения |
| [speech-operator-compare.dify.yml](../dify/speech/speech-operator-compare.dify.yml) | Сравнение классификации с выбором оператора |

YAML хранит шаги, промпты и формат входа/выхода для ручного импорта в отдельный
сервис Dify. Воркер вызывает уже импортированное приложение через
`/workflows/run`, используя адрес и ключ из настроек. В процессе обработки
YAML с диска не читается; изменение файла не обновляет внешнее приложение
автоматически. Перенос файлов не меняет действующие сценарии и внешний Dify.

Проверки файлов и согласованности их контрактов с кодом остаются здесь:
`tests/test_speech_dify_workflow.py`, `tests/test_speech_fill_reasons.py`
и `tests/test_speech_free_workflows.py`. Тесты не требуют исходников бэкенда.
Оценка операторов по скрипту обращается прямо к LLM и от этих файлов не зависит.

Внешний `local-dev/run.sh` при выборе `speech-backend` читает сценарий анализа
из этой папки для локальной заглушки. Это только инструмент разработки;
сборка и запуск API не требуют исходников воркера.

## Контракты и состояние переноса

Очередь и таблицы результатов общие с `speech-backend`. Миграции принадлежат
бэкенду; требуемая ревизия — `sp_0015_drop_masking`.
Форматы и границы владения описаны в [контракте разделения 1.0](contracts.md).
Проект собирается без исходников соседнего репозитория.

12.10.2026 фоновые команды и их зависимости выделены из копии в
`speech-backend`. Перенесены существующие тесты очереди, этапов, источников,
хранилища и оценки; добавлены проверки запуска, закрытия ресурсов и очистки
после аварии. Настройки API и политики хранения других приложений исключены.

Python-реализация в `speech-backend` и исходный `whisper-backend` сохранены.
Dockerfile и Compose предназначены для независимого запуска на сервере;
удалённый сервер пока не переключён. Подключение GigaAM — отдельная будущая
работа, текущая реализация и настройки к нему не привязаны.
