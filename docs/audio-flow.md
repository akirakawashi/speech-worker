# Путь аудио и размещение обработки

Воркер выделен в самостоятельный проект и предназначен для GPU-сервера
без Kubernetes. Сейчас он вызывает существующий Whisper по HTTP.
MinIO находится на другой машине; внутренняя сеть — 10 Гбит/с по словам владельца.
GigaAM в текущей реализации отсутствует.

## Как работает текущий код

1. Воркер берёт задание из PostgreSQL, таблица очереди — `speech_jobs`.
2. `ingest` скачивает запись источника во временный каталог,
   измеряет её через ffprobe и сохраняет оригинал в MinIO.
   Существующий объект повторно не загружается из источника.
3. `transcribe` скачивает оригинал из MinIO в свой каталог
   и создаёт WAV mono 16 кГц через ffmpeg.
4. Клиент читает WAV в память вне event loop и отправляет один multipart-файл
   в `/audio/transcriptions` сервиса Whisper. Ссылка на MinIO не передаётся.
5. Whisper возвращает текст и таймкоды. Воркер определяет роли по энергии
   каналов оригинала, отсекает сегменты после конца аудио и очищает свой каталог.
6. Воркер сохраняет готовый DTO в буфер PostgreSQL и доставляет бэкенду.
   Бэкенд одной транзакцией сохраняет расшифровку, завершает задание,
   ставит `analyze` и убирает буфер. При сбоях DTO восстанавливается без WAV.
   Основной воркер не вызывает LLM; сохранённый анализ исполняет CPU-команда
   бэкенда `speech-process`; оценка выбирается независимо по расписанию.
   [Доставка, квитанция и восстановление](transcription-delivery.md).

Исходники: [приём](../src/application/pipeline/ingest.py),
[распознавание](../src/application/pipeline/transcribe.py),
[клиент](../src/infrastructure/clients/whisper.py),
[multipart-транспорт](../src/infrastructure/transcription/providers.py),
[очистка каталога](../src/infrastructure/media/workspace.py).

## Ответственность за очистку

| Файл | Где находится | Кто очищает |
|---|---|---|
| Скачанный оригинал и подготовленный WAV | Каталог воркера на GPU-хосте | Воркер после завершения операции, ошибки или отмены |
| Принятое аудио и промежуточные файлы Whisper | Контейнер Whisper на GPU-сервере | Сервис Whisper |
| Постоянный оригинал | MinIO на отдельном сервере | Отдельная команда по правилам хранения |

`SPEECH_WORKER_TEMP_DIR` задаёт отдельный корень аудиокопий.
Каталоги этапов создаются с меткой задания и файлом блокировки Linux.
Блокировка удерживается до выхода из контекста; обычная ошибка и отмена
также проходят через удаление каталога.

После аварии ОС освобождает блокировку. При следующей сборке воркера уборка
удаляет только собственные каталоги со свободной блокировкой. Активные каталоги,
каталоги без метки и символические ссылки пропускаются. Создание и уборка
защищены общей блокировкой корня, поэтому другой запуск не удалит создаваемый
каталог. Поведение проверено [тестами очистки](../tests/test_worker_workspace.py),
включая отдельный процесс, завершающийся без finally.

В ранее изученной конфигурации контейнера Whisper каталоги `/run/whisper-temp`
и `/tmp` находятся в tmpfs. Удаление после каждого запроса в установленном
образе и фактическая конфигурация работающего сервера ещё не проверены.
Локальная очистка воркера не подтверждает очистку внутри Whisper.

Весовые файлы существующей модели принадлежат контейнеру Whisper.
Удаление оригиналов из MinIO после распознавания не выполняется; отдельный
сценарий `speech-prune` сохраняет прежние правила хранения и по умолчанию
работает в режиме проверки.

## Размещение и скорость

Путь записи: MinIO → временный каталог воркера на GPU-хосте →
подготовка WAV → HTTP-интерфейс существующего Whisper на этом сервере →
результат в PostgreSQL.

Скачивание из MinIO остаётся сетевой операцией. GPU использует Whisper,
подготовка аудио и прикладная обработка требуют CPU.
Фактическое время передачи и нагрузка модели на сервере не измерены.

Для PCM mono 16 кГц, 16 бит расчётный объём часа — примерно 115 МБ.
При 10 Гбит/с теоретическая передача такого объёма занимает около 0,09 с.
Чтение, запись, HTTP, прокси и конкуренция за сеть в этот расчёт не входят.
Скорость конвейера проверяем замерами скачивания, подготовки, ожидания
и распознавания. Размещение выбрано владельцем; оно не заменяет измерений.

## Параллелизм и батчи

Один процесс выполняет одно задание за раз и отправляет один файл в Whisper.
Батчи и повышение параллелизма отложены. В Compose запускается один воркер
с полосами `daily,backfill`: история выполняется после более срочных звонков.

В базе сохраняется прежняя настройка `transcribe_concurrency`
с умолчанием 2. Это общий предел допущенных операций для нескольких
процессов, а не запуск второго обработчика внутри одного воркера.
Установленное значение может быть переопределено настройками в базе;
первый запуск проекта не изменяет эту настройку автоматически.

Источники: [цикл воркера](../src/infrastructure/queue/worker.py),
[настройки по умолчанию](../src/domain/calls/contracts.py),
[слот этапа](../src/application/pipeline/transcribe.py).

Группировка файлов в HTTP-запрос, несколько одновременных запросов и
вычисление батчем внутри модели — разные механизмы. Ни один новый режим
этим выделением не добавлен. Если вернёмся к батчам, отдельно проверим
скорость, видеопамять, качество текста, таймкоды и задержку результата.

## Переход на GigaAM

Исследование сохранено для будущего этапа. По текущему решению владельца
GigaAM пока отсутствует: адаптер, загрузка модели, параметры CUDA и
зависимости библиотеки в код не добавлены. Текущий воркер использует Whisper.

Ранее проверена официальная документация и код `salute-developers/GigaAM`:

- [Загрузка аудио](https://github.com/salute-developers/GigaAM/blob/main/gigaam/preprocess.py)
  запускает ffmpeg с выводом PCM в stdout и создаёт тензор в памяти.
- [Методы распознавания](https://github.com/salute-developers/GigaAM/blob/main/gigaam/model.py)
  возвращают готовый результат и не удаляют входной файл.
- [Разбиение длинного аудио](https://github.com/salute-developers/GigaAM/blob/main/gigaam/vad_utils.py)
  создаёт фрагменты как срезы тензора в памяти, без записи отдельных аудиофайлов.
- [Официальный README](https://github.com/salute-developers/GigaAM/blob/main/README_ru.md)
  указывает обычный transcribe для файлов до 25 секунд и transcribe_longform
  для длинных записей.

Вывод из кода библиотеки: временный входной файл можно удалять после полного
завершения распознавания. Сопоставимость таймкодов, длинные звонки и очистку
потребуется проверить при отдельной реализации этого будущего этапа.
